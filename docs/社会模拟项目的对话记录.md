## 一、关于"快动作慢思考"——这是整套架构的核心，必须深入
你提的这个洞察，**比向量检索/缓存优化更重要**。它决定了游戏的"体感"，也决定了一切其他设计。让我把它具体化。
### 1.1 "为什么 LLM 延迟可以被完全隐藏"
人类大脑也是这样工作的。你走在路上时，大脑已经在想到家之后干什么；你说一句话之前，下半句还没成型。**思考永远比执行超前一步**。
我们的架构应该模仿这个：每个 agent 维护一个 **Action Queue（行动队列）**——一个按时间排好的"我接下来要做的事"清单。游戏循环只负责按队列执行，**它从来不等 LLM**。LLM 在背景里异步思考，结果到达后追加到队列尾部。
具体例子。林夏当前 Action Queue：
```
[当前] walk_to_kitchen      还要 5.5 秒
[+1]   make_breakfast       预计 15 秒
[+2]   eat                  预计 10 秒
[+3]   walk_to_bar          预计 20 秒
[已规划总时长：50.5 秒]
```
游戏在 T=0 时启动一个 background thinking：「林夏吃完早饭打算去酒吧之后，做什么？」LLM 在 T=2.5 秒返回 `chat_with_zhouming(60s)` 和 `leave_bar(5s)`。这俩动作追加到队列尾部。从玩家视角，林夏一直在流畅地走路、做饭、吃饭，**完全感受不到 LLM 的存在**。
### 1.2 队列水位与触发机制
队列不能空。当 `已规划剩余时长 < 阈值（30 秒）` 时，立即触发新一轮思考。这里有几个关键参数我建议这样设：
- 触发阈值：30 游戏秒
- 单次思考输出：3-7 个动作（足够覆盖几分钟）
- LLM 实际延迟容忍上限：10 秒（超过用 fallback）
- Fallback 策略：如果队列空了 LLM 还没返回，agent 执行 `idle(短)` 或重复上一个无害动作
### 1.3 紧急打断机制
不是所有事件都能等 30 秒后再处理。如果林夏在做饭时听到走廊里有惨叫（importance ≥ 8 的事件），她需要立刻反应。
我设计的优先级机制：
**当前正在执行的原子动作不可打断**——做饭做了一半，物理上不能立刻停下扔锅就跑。原子动作必须执行完。
**但队列后段可以重排**——做饭剩 4 秒，剩下的 4 秒 + 弹出 `eat`、`walk_to_bar` 等后续动作，立刻发起紧急思考：「林夏听到惨叫，做完饭后她要做什么？」LLM 返回新序列覆盖原队列后段。
**对话进入特殊模式**——对话不走 Action Queue。当两个 agent 进入对话状态，它们的队列暂停，进入对话状态机；每说一句话本身需要 2-4 秒的"打字+显示"时间，LLM 用这段时间生成下一句。对话结束后 agent 退出对话状态，重新启动队列。
### 1.4 这种架构的副产物：你能"看见"思考
因为思考是异步的，UI 上可以加一个**"思考指示器"**——agent 头顶有时浮现一个小小的灯泡 emoji（💭），表示"它正在背景中规划"。这不仅好看，还把 AI 的不确定性变成了可见的设计语言。**玩家会主动等待 agent "想好"**，而不是抱怨"它怎么不动"。
这是个非常巧妙的玩法转化。

## 二、关于不用向量检索——基于 V4-Pro 的能力，可行且更优
V4-Pro 的 1M 上下文 + 0.025 元缓存命中价，让你这个判断**不仅可行，反而是最优解**。让我量化一下。
DeepSeek V4-Pro 总参数 1.6T、激活参数 49B，原生支持 1M tokens 上下文 + 384K tokens 最大输出，并默认启用上下文缓存。V4-Pro 限时 2.5 折后，缓存命中输入仅 0.025 元/百万 tokens，缓存未命中输入从 12 元降至 3 元，输出从 24 元降至 6 元。
这个价格结构意味着什么？**输入缓存命中部分的成本几乎可以忽略**（命中价是未命中价的 1/120）。所以策略是：**让 95% 以上的输入 tokens 都命中缓存**。
### 2.1 Prompt 分层缓存设计
我建议把每次 LLM 调用的 prompt 切成 4 层，从稳到变排序：
```
┌─────────────────────────────────────────────┐
│ Layer 0：世界观 + 全员人设速览（~5K tokens） │  ← 永远不变，跨所有 agent 共享
│ Layer 1：当前 agent 完整人设（~2K tokens）   │  ← 几乎不变，跨 tick 保持
│ Layer 2：最近 30 分钟世界事件（~8K tokens）  │  ← 半小时更新一次
│ Layer 3：当前情境 + 决策提示（~2K tokens）   │  ← 每次调用都变
└─────────────────────────────────────────────┘
```
DeepSeek 的缓存机制是**前缀匹配**——只要你的 prompt 前 N 个 token 和之前某次调用一样，前 N 个就命中缓存。所以**绝对不能把变化的内容放前面**。把 Layer 0-2 严格按这个顺序拼接，Layer 3 永远在最末尾。
单次调用成本估算（V4-Pro 限时折后价）：
| 部分 | tokens | 单价（元/M） | 成本 |
|------|--------|-------------|------|
| Layer 0-2 命中 | 15K | 0.025 | 0.000375 |
| Layer 3 未命中 | 2K | 3 | 0.006 |
| 输出 | 500 | 6 | 0.003 |
| **小计** | | | **约 0.0094 元/次** |
10 agent × 100 次/agent/游戏日 = **约 9 元/游戏日**。如果游戏内 1 日对应现实 1 小时，1 小时玩耍约 ¥9。**完全可控**。
### 2.2 Memory 检索的实现：In-Context Recall + 关键词粗筛
不用 embedding，但也不能把 agent 全部记忆都塞进 prompt（agent 跑了几天后记忆会很多）。我的方案：
**两层过滤**：
**第一层（关键词粗筛，纯 Python，0 成本）**：从当前情境提取关键词（位置名、人名、最近重要事件），在 SQLite 里 LIKE 查询出**所有可能相关**的 memory。这一步不要追求精准，宁可多召回。
**第二层（让 LLM 自己挑）**：把粗筛出来的 memory（限制 50 条以内）连同当前问题一起放进 prompt 的 Layer 2，让 V4-Pro 自己在 in-context 里做精排。它的判断比 cosine similarity 准得多。
**记忆压缩策略**：
- 最近 24 游戏小时的 memory：**全保留**，原文塞入
- 1-7 天前的 memory：**按 importance ≥ 5 保留**，importance < 5 的合并成"日常摘要"
- 7 天以前的 memory：**只保留 reflection 和 importance ≥ 7 的事件**
这种压缩可以在每个游戏日结束时批量做，开销极低。
### 2.3 对延迟方差的应对
我搜索时注意到一个细节，实测中 V4-Pro 的响应延迟方差较大，有时很快，有时明显变慢；对需要稳定响应时间的生产环境是个真实问题。这正好是我们用快动作慢思考架构必须解决的问题。
应对手段：
**一是设硬超时**——单次 LLM 调用 8 秒超时，超时立即用 fallback 动作。
**二是双管道并发**——重要 agent（玩家正在观察的）走 V4-Pro，背景 agent 用 V4-Flash。Flash 比 Pro 便宜十倍且延迟更稳。
**三是预热缓存**——游戏启动时主动发一次 Layer 0+1 的 ping 调用，让缓存"热"起来。

## 四、美术素材清单 + Claude Code 怎么用你的图
### 4.1 直接答你的问题
**Claude Code 完全可以使用你上传的图片**。流程：
1. 你把图片放到约定的目录（比如项目里的 `assets/characters/lin_xia/idle.png`）
2. Claude Code 写 Godot 代码时直接引用路径 `res://assets/characters/lin_xia/idle.png`
