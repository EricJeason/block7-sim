## 项目定位刷新(重要,可能纠正了上一轮的理解)

这是一个 **生成式 NPC 社会模拟器 + 类 RPG 框架**。
**类 RPG ≠ 传统任务驱动 RPG**:
- 没有显式 quest acceptance、没有打怪升级、没有装备成长曲线
- 但**有**类 RPG 的栏目框架(角色 / 背包 / 任务/线索 / 图鉴)
- 这些栏目的存在不只为当前内容服务,**主要是为未来玩家自定义剧本(模组)预留标准化容器**

**核心设计原则**:框架开放、功能齐全。每个 UI 容器都应该想象成"未来某个玩家可能往里塞什么内容",而不只是当前实装。这意味着设计稿要给 schema 不只给 visual。

## 二、本轮修改

### 修改 1 · NPC pixel sprite 风格升级到 anime-pixel(最重要)

上一轮 14×22 极简 sprite **不是目标风格**。新规范:

- **风格参考**:anime-style 详细像素艺术(Granblue Fantasy 立绘像素版 / 月华剑士 / 专业 RPG Maker)
- **walking sprite**:64×128 像素
- **portrait**(S11 对话 / S4 笔记本 / C 角色面板 / P 图鉴):256×256 bust shot
- **必备细节**:脸部表情可读、服饰细节(职业相关)、头发衣服在 walk 帧有流动感
- **变体要求 · 每个 NPC 3 套状态**:
  - (a) **正常态** — 日常
  - (b) **感染态** — 红眼 + 苍白 + 衣物破损(参考 Eric 提供的艾琳样图)
  - (c) **治愈者潜在标记** — 跟正常态几乎一样,只名牌晕 + 夜间梦境碎片有 #7A5A96 元素

**参考图**:Eric 会在对话中提供 3 张艾琳样图作为 ground truth。请向 Eric 索取。

**本轮交付**:1-2 个 NPC(建议林秋 + 千绫)的正常态 + 感染态 sprite + portrait,作为风格示范。其余 11 个 NPC 资产 Eric 后续找美术或 AI 像素生成器补,**不强求 Design 全画**。

### 修改 2 · S5 关系网的"渐进解锁"机制

紫圈不是常驻 label,是玩家累积"线索阈值"后系统才标的。

- **三态展示**(替代当前直接显示紫圈):
  - 0 分 → **无标记**
  - 1-2 分 → **节点边缘灰色虚线圈**("觉得哪里不对")
  - 3+ 分 → **紫色实线圈**("已确认治愈者")
- **线索积分来源**(后端逻辑,UI 不显示积分):
  - 看见 NPC 夜间梦境碎片粒子 +1
  - 与 NPC 对话中提到"梦" +1
  - 通过另一 NPC 听到关于这个人的传闻 +1
- **hover 显示"观察记录"** tooltip:"你对 TA 的了解:近距离 2 次 / 听说 1 次 / 直接对话 3 次"

请在 S5 mockup 上画出三种观察状态的视觉差异。

### 修改 3 · 走近 NPC 的 whisper 要带 NPC 名字

格式:`NPC名 · action描述`(两行或单行均可,字号见原 brief)。仅当距离 < 100px 显示,走开消失。请更新 S3 主屏 mockup。

### 修改 4 · S11 对话改为"LLM 选项 + 自由输入"混合模式

- **保留 3 个 LLM 候选**(快速、低输入成本)
- **下方加自由输入框**(modal 底部 1/3 高度)
- **关键交互**:
  - 点候选 → 自动填入输入框 → 玩家可编辑 → 发送或回车
  - 候选按钮上有 ✎ 图标 = "复制到输入框编辑"
  - 候选旁边小 → 按钮 = "直接发送原候选"
  - 输入框 placeholder:"或在这里写你自己的话…"
- **读秒机制**:
  - 提交后系统按字数计算延迟 `max(2, 字数 × 0.15)` 秒
  - 这段时间 NPC 头顶 "…" 思考态,玩家不能再输入
  - 延迟结束后 NPC 回复出现

请重画 S11 mockup,展示这个混合输入区。

**属性双层设计**(关键):
- **显性属性**:有数字 + 进度条,玩家可见(健康 / 疲劳 / 饥饿 / 情绪)
- **半显症状**:无数字,文字描述,玩家可见但只是"症状",不知道背后是什么数值(感染度 / 心理负荷 / 创伤值等)——**这是 horror 项目最重要的设计**
- **隐性属性**:面板**不展示**,只在后端驱动 NPC/玩家行为。例:"是否治愈者"、"对林秋的好感度"、"性格内向程度"——这些 LLM 用,玩家不直接看到,只能通过观察行为推测

**剧本可注入字段**(给未来模组系统的 schema):
```yaml
visible_stats:
  - { id, name, max, current, color, icon? }
semi_visible_symptoms:
  - { id, text, condition }  # 满足 condition 时显示
hidden_attributes:
  - { id, value, drives: [behavior_tag] }  # 后端用,UI 隐藏
equipment_summary:
  - { slot, item_id, effect? }
```

**容量机制**(可变):

- 未来如果实装"偷窃/交易/给予"机制,玩家与 NPC 互动菜单里会出现"交换物品"选项

## 八、设计哲学:框架开放,服务剧本

本轮所有新增容器(C/I/J/P)的根本目的:**给未来玩家自定义剧本/模组系统提供标准化数据接入点**。

每个容器都暴露一套 schema(yaml-like),未来玩家写一个剧本可以:
- 在 C 里注入新的属性维度("好感度·林秋" / "对寂塔的痴迷" 等)
- 在 I 里注入新物品("古老的解药配方" / "陌生人的信" 等)
- 在 J 里注入硬任务("追查父亲笔记缺失的第 17-19 页")
- 在 P 里注入新 NPC 字段("XX 的童年照片"——条件解锁)

设计师不需要为每个未来内容画一遍稿。**容器的标准化结构本身就是设计**。Mockup 展示当前默认状态 + 未来"如果剧本注入了某些数据"的占位状态(灰色/半透明示意),让 Eric 看到这个接口长什么样。

**核心:框架本身是 design,不只是 content 的容器。**
